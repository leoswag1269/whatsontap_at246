# CLAUDE.md — whatsontap_at246 (Home Tap)

## What this is
A public guest taplist for Leo's home bar, served by GitHub Pages. The source of truth is Leo's Notion Draught Hub (Taps → Kegs → Recipes). A scheduled GitHub Action pulls from Notion, regenerates `data/taplist.json`, and commits only when guest-visible content changed. The commit history doubles as the keg changeover log.

**Read first:** `docs/2026-10-16-home-tap-sync-prd.md`. It is the spec. If a request conflicts with it, say so before acting.

## Layout
- `index.html`: the page (design, CSS, renderer). It reads data from `data/`.
- `data/taplist.json`: GENERATED by `scripts/sync.py`. Never hand-edit.
- `data/bottles.json`: hand-edited by Leo.
- `data/styles.json`: GENERATED from `styles/style-guidelines.md` (Milestone 3).
- `scripts/sync.py`: Notion → JSON. Python 3 standard library only.
- `tests/`: unit tests plus fixtures. Run with `python -m unittest discover tests`.
- `.github/workflows/sync.yml`: hourly and manual sync.

## Hard rules
1. **Privacy allow-list.** Only fields listed in PRD §5 may reach any file in this repo. Add a field only with Leo's explicit approval, and add it to the privacy test in the same change. Never output Kegs `Notes`, volumes, disposition, quality, repairs, locations, any Recipes personal/sharing/Gemini/nutrition fields, or Notion page URLs or IDs.
2. **No secrets in the repo.** The Notion token lives only in GitHub secret `NOTION_TOKEN`. Database IDs live only in Actions variables. Never print them, put them in fixtures, or commit `.env` files.
3. **Notion is read-only.** Never write to Notion from this project.
4. **Git flow.** Work on a branch and open a PR. Never push to `main`, force-push, rewrite history, or delete branches you didn't create.
5. **Ask before:** deleting files, changing the workflow schedule or permissions, adding a dependency, or changing the page's visual design. When you ask, show what will change and wait for an explicit "proceed".
6. **Don't hand-edit generated files** (`data/taplist.json`, `data/styles.json`). Fix the generator instead.

## How to work
- **Start every task in plan mode.** Explore, propose a plan, wait for approval, then build.
- **Definition of done:** tests pass (including the privacy test). For any page change, also take a preview screenshot rendered from fixture data. Include both in the PR.
- After each major step, give a 2–3 line summary: what you did and what's next.
- Flag contradictions (PRD vs. request vs. existing code) before acting. Never silently overwrite a prior decision.
- Interrogate vague requests instead of guessing.

## Communicating with Leo
- Leo is a scientist and an experienced AI user, but not a terminal user. He reviews diffs in GitHub Desktop and the GitHub web UI. Write PR descriptions in plain language: what changed, why, how it was verified, and anything he must do.
- Show reasoning, not just conclusions. Skip filler. Disagree openly when something's off.
- When the session's context is getting long, or the next task is unrelated, suggest starting a fresh session.

## Conventions
- New docs go in `docs/` as `YYYY-MM-DD-descriptive-name.md`. Exceptions where tooling expects fixed names: `CLAUDE.md`, `README.md`, `data/*.json`, and workflow files.
- Commit messages for data syncs come from the generator. For code changes, use short imperative messages.
- Keep `index.html` self-contained, with no build step and no frameworks.
